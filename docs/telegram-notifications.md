# Telegram 通知

在「系统设置 → 设备与通知」中启用 Telegram，填写 Bot Token 和管理员 Chat ID，保存后可发送测试消息。管理员私聊可使用 `/start`、`/strm_inc`、`/sync`、`/status` 和 `/cancel` 控制 STRM 同步；群组 Chat ID 只接收通知。

## 入库通知

Telegram 配置就绪后，本地扫描、文件监控或整理入库新增的电影、剧集，会发送海报与入库通知。115/OpenList 的 STRM 文件被扫描进 Nook 媒体库后，同样会触发通知。只有生成 STRM、尚未扫描入库时不会触发；远程 Emby 挂载浏览也不属于本地入库。

通知包含片名、年份、媒体库、评分、类型、最多五位主演、入库时间和简介；剧集另外显示季集号。缺少的字段省略。简介按 Telegram 图片说明的 1024 字符限制截断。

同一媒体库、同一部剧连续入库的多集合并为一条通知，海报、主演和简介只发送一次。例如 `集数：S01E11–E12 · 新增 2 集`。不连续的集数分别列出，跨季分别标明季号，同一集的多个版本不重复计算集数；电影继续逐部通知。

- 沿用现有 Telegram 总开关、Bot Token 和管理员 Chat ID，无需额外账号或通知配置。
- 首次运行建立已有媒体的基线，不推送整个历史媒体库。关闭期间新增的影片不补发；更换机器人或接收会话也会重新建立基线。
- 以媒体首次创建时间和 ID 记录发送进度，普通重扫、改名和更新元数据不触发重复通知。进度保存在 `settings` 的 `telegram.media_ingest_cursor` 中，正常重启后继续处理尚未发送的新增记录，不包含 Token 或媒体链接。
- 通知由单个后台任务依次发送，每次发送至少间隔一秒。入库流程无需等待 Telegram；限流时遵守 `retry_after`，失败不会回滚媒体入库。
- 启动时建立通知基线最多等待两秒，失败后交给后台重试；后台每轮处理也有三十秒总超时，避免数据库或网络异常长期占用通知任务。
- 新记录至少等待十秒，让数据库写入和元数据处理稳定。待刮削记录最多等待五分钟，随后用已有信息通知，防止没有启用刮削的影片一直阻塞后续通知。
- 剧集在最后一集入库后额外等待三十秒收集同批更新，单批收集时间最多两分钟，每轮最多查看两百条新增记录。剧集 ID、TMDb/Bangumi/TVDB/Douban ID 优先；缺少 ID 时使用媒体库、剧名及年份匹配。后续批次新增的剧集仍会发送新的通知。
- 合并跨过中间的电影或其他剧时，另外保存已发送集数的进度，只有中间内容处理完才推进主游标，避免漏发其他影片；这些进度同样支持重启恢复，不增加表或修改媒体数据。
- 主演复用 Nook 的演职员缓存、TMDb/NFO 查询，查询最多等待四秒，失败不影响入库通知。通知不进行视频探测。
- 本地海报只允许读取配置的图片/媒体目录；远程海报沿用图片代理的检查和缓存。上传图片本身，Telegram 无需访问 Nook 或获得图片链接中的凭据。图片缺失、不可读或被 Telegram 明确拒绝时，回退为文字通知；网络错误、认证失败或限流保留记录等待重试。

新增一个按 `(created_at, id)` 排序的媒体索引，用于增量查询；不新增表，也不修改已有媒体内容。发送成功后才保存进度；如果 Telegram 已收到消息而进度保存失败，重试时可能再次发送该条通知。

图片和说明长度依据 [Telegram 官方 sendPhoto 文档](https://core.telegram.org/bots/api#sendphoto)。
